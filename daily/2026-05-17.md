## 📖 章节精读摘要

### 1️⃣ 智能体（Agent）

🔗 原文：https://aiweb3.school/zh/handbook/ai-basics/agent
⏱️ 阅读约 6 分钟 | 约 1799 字

**一句话总结**
Agent 是能围绕目标持续调用工具、读取状态、调整步骤的 AI 系统。关键不在"像人"，而在能不能在明确权限和可审计流程里把建议推进到行动。

**核心观点**

- LLM 生成文本 → Agent 进一步拆任务、查资料、调用 API、写代码、等待反馈再继续
- ⚠️ **风险点**：错误从"答错"变成"做错"——工具调用、写入系统、触发支付都有真实副作用
- 学 Agent 不是追逐框架，而是建立分工：**模型提候选 → 系统限空间 → 用户批高风险**

**第一性原理**
Agent = 被约束的执行循环。5 个缺一不可的要素：
1. **目标** — 要做什么
2. **工具** — 能调什么
3. **状态** — 进度如何（必须外置可查，不能只藏 prompt 里）
4. **权限** — 能做什么不能做什么
5. **停止条件** — 何时停（目标达成 / 超预算 / 信息不足 / 风险越界 / 用户拒绝）

**4 大知识节点**

| 节点 | 要点 |
|------|------|
| **Tool Use** | 工具让 Agent 从"会回答"变"能做事"。设计工具要明确：输入 schema、权限范围、是否只读、是否有外部副作用、哪些需人工确认 |
| **Planning** | 把目标拆步骤。计划只是候选路线不是授权。越靠近高风险动作越需要系统规则检查。好 plan 应暴露：每步用什么工具、读写属性、自动/确认、失败重试策略、完成验证方式 |
| **State** | 任务状态 = 目标 + 已完成步骤 + 工具返回 + 错误 + 预算 + 确认记录 + 最终输出。生产系统需要可查询、可恢复、可审计的 state |
| **Reflection** | Agent 自检中间结果并修正。但自我反思仍由模型完成，模型可能给自己的错误找理由。**自我检查提高质量，确定性检查才能承载风险** |

**Multi-Agent 注意事项**
- 多 Agent 分工适合复杂工作流（研究 / 开发 / 安全审查 / 执行）
- 但会放大问题：上下文丢失、责任边界模糊、错误被当事实传播、权限扩散
- 🔑 先问：多 Agent 是否真的减少复杂度？还是只是把不清楚流程拆成多个不清楚角色？

**AI × Web3 中的位置** — Agent 架构（7 步）：
```
用户提出目标和约束
→ Agent 读取上下文并生成计划
→ 系统拆成只读步骤和候选写入步骤
→ 只读工具自动执行，写入工具进入 policy 检查
→ Simulation 展示链上影响
→ 用户确认高风险动作
→ Wallet / Smart Account 执行
→ 日志记录每一步和最终状态
```

⛔ 最危险的设计：**让 Agent 同时拥有模糊目标 + 广泛工具 + 长期记忆 + 大额资产权限**

**最小实践建议**：做一个「DAO 提案研究 Agent」— 只读版本（读取提案、检索讨论、总结正反理由、标记缺失信息、输出投票前检查清单），不直接投票。

### 2️⃣ 链感知上下文（Chain-aware Context）🔥 Bridge 入门核心

🔗 原文：https://aiweb3.school/zh/handbook/bridge/chain-aware-context
⏱️ 阅读约 5 分钟 | 约 1632 字

**一句话总结**
让 AI 在回答或行动前，能看见正确的链、地址、合约、交易、事件、余额、授权和数据来源，而不是只靠用户一句话猜测链上状态。

**为什么重要**
- 普通 AI 上下文来自文档、聊天历史、数据库、网页
- AI × Web3 多了一层：**链上状态持续变化**，且与资产、权限、交易执行直接相关
- Agent 不知道 chain id、合约地址、ABI、用户授权、交易历史 → 可能给错误建议甚至生成危险交易

**第一性原理（3 条铁律）**
1. **模型不能凭语言记忆判断链上事实** — 必须从工具和索引层读取
2. **链上状态有时间性** — 同一地址余额/授权/仓位随区块变化
3. **上下文要区分事实和解释** — 工具返回事实，模型负责解释，不要把猜测当事实

**7 大知识节点**

| 节点 | 难度 | 核心要点 |
|------|------|---------|
| **On-chain Data** | 初级 | RPC / 浏览器 / 索引器 / 协议 API。读取时至少带：chain id、block number、contract address、method、返回值、读取时间。缺少这些字段容易混链混时间 |
| **Contract Docs** | 初级 | ABI 只告诉函数签名，不解释业务语义（如 `execute(bytes)` 可能是高权限入口）。文档可能过期，要用链上数据交叉验证 |
| **ABI / Event** | 中级 | ABI 编码调用/解码返回/解析事件；Event 是合约的业务日志（Transfer/Swap/Deposit/VoteCast）。⚠️ 能调用 ≠ 应该调用，写交易前还需权限/余额/allowance/slippage/simulation/policy 检查 |
| **Transaction History** | 中级 | 判断授权状态、策略执行历史、高风险交互、合约升级。保留 tx hash/block/from/to/method/value/token transfers/logs，证据必须能回链上 |
| **Explorer Context** | 初级 | 区块浏览器提供可视化链上证据。产品里给 explorer link 比"交易成功"更可靠 |
| **Indexing Context** | 中级 | 把事件整理成面向产品的查询（如"用户30天DeFi操作"）。必须带时间戳和同步状态，落后500区块的结果不应被当当前事实 |
| **Citation** | 初级 | 让回答回到具体链上证据（tx hash/区块号/合约地址/event log/explorer链接/文档URL）。无 citation = 观点；有 citation = 可验证可追责 |

**在 AI × Web3 中的位置**
Chain-aware Context 是所有链上 Agent 的**输入层**。没有这层，Web3 Tool Use、Agent Workflow、Agent Wallet 都建立在不可靠上下文上。

**一个好的链感知上下文包应包含：**
- 用户目标
- 当前 chain id 和网络名称
- 用户地址和余额
- 相关合约地址、ABI、文档和风险提示
- 最近交易和授权
- 索引数据更新时间
- 每条关键结论的 citation

**最小实践建议**：找一笔公开交易哈希 → 收集完整字段（chain id/block/from/to/method/value/transfers/logs）→ 找 ABI 或 verified source → 写模型可读上下文，每个结论附 citation → 标注事实 vs 解释

## 💡 两章关联思考

Agent 章节讲了 **"怎么执行"**（Tool Use / Planning / State / Reflection），Chain-aware Context 讲了 **"执行前要知道什么"**（链上数据/合约语义/交易历史/citation）。两者结合：

> **Agent 的 State 不能只放 prompt 历史，必须包含 Chain-aware Context 提供的可验证链上事实；Agent 的 Tool Use 在 Web3 场景下，每个工具调用都要带 chain id / block number / contract address 等元数据。**

这就是 Bridge 层的核心逻辑 —— AI 的执行能力 + Web3 的可验证状态。
