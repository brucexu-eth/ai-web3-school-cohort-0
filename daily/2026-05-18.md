## Chapter notes — Web3 Tool Use

Core claim: Web3 Tool Use turns RPC, contract reads, transaction generation, wallet confirmation, explorers, and DeFi operations into Agent-callable tools. The hard part is not “can the model call it”, but permission, parameters, simulation, and audit logs.

First principles:

- Model may choose tools, but deterministic boundaries must constrain tool execution.
- Read/write must be separated.
- Parameters such as chain id, contract address, method, args, value, and slippage must be structured, not hidden in natural language.
- Every call needs logs: input, output, time, source, error, chain id, block number, tx hash, confirmation, and policy result.

Minimal artifact checklist:

| Tool | Risk | Required boundary |
|---|---|---|
| RPC read | Low / medium | chain id, provider, block number, method, result |
| Contract read | Medium | verified contract, ABI match, network check |
| Transaction draft | High | no broadcast, explicit calldata, simulation-ready |
| Wallet action | High | separate connect / sign / send / approve / revoke |
| DeFi action | Very high | protocol whitelist, amount cap, slippage cap, simulation, allowance check, human or policy confirmation |

## Chapter notes — Agent Workflow

Core claim: Agent Workflow turns “user goal → context read → plan → tool call → risk check → execution → record/review” into a controlled process instead of free-form model behavior.

First principles:

- High-risk Agent systems cannot rely only on next-token reasoning; they need state, boundaries, and stopping conditions.
- Workflow must be explicit, recoverable, and replayable.
- Trace and regression sets are not observability nice-to-haves; they are safety infrastructure.

Minimal workflow skeleton:

```text
user_goal
→ load_chain_context
→ check_balance_and_allowance
→ query_price_and_liquidity
→ draft_transaction
→ simulate_transaction
→ policy_check
→ human_confirmation_if_required
→ submit_or_cancel
→ track_receipt
→ write_trace_and_daily_note
```

State examples:

```text
draft → context_loaded → plan_ready → simulation_failed / waiting_user_confirmation → submitted → confirmed / reverted / cancelled
```

Core insight: wallet confirmation is insufficient for Agentic Commerce. The user needs one combined approval boundary that covers:

1. intent confirmation — what exactly is being bought;
2. payment confirmation — how much ETH / which route / which recipient;
3. privacy confirmation — what personal data is disclosed to whom;
4. audit confirmation — what receipt is saved for future review.

Current flow decision: for the demo, the swap / bridge / payment route confirmation can be merged into the final payment confirmation, as long as the approval card clearly shows product, route, amount, recipient, chain, fee, slippage, privacy disclosures, and wallet action before any signing or sending.

## Tool / permission notes from today

Checkout Agent likely needs:

- Tool log: durable record of inputs, outputs, source, timestamp, policy result, error, chain id, block number, tx hash, and confirmation state.
- Tool permissions: central policy gate before risky tool calls.
- Balance query: ETH/session-wallet balance and maybe allowance.
- Transaction draft: prepare calldata / route without signing or broadcasting.
- Small-amount whitelist payment: possible narrow policy for low-value payments, but only with caps on asset, amount, recipient, chain, expiry, and frequency.
- DeFi tool: swap / bridge / token movement when direct ETH payment is impossible.
- Explorer tool: verify final transaction status, recipient, confirmations, and events.
- Wallet tool: connect / sign / send / approve / revoke boundary.
- Contract read/write: reads for state and allowance; writes only after explicit confirmation.

Dangerous tools / boundaries:

1. Tool permissions.
2. DeFi tool.
3. Wallet tool.
4. Contract write.

Handbook feedback: Web3 Tool Use should include more detailed examples, especially an Agentic Checkout example showing tool log, permissions, balance query, transaction draft, small-value whitelist, DeFi route, explorer verification, wallet action, contract read/write, and which tools are dangerous.
