## Chapter notes — Web3 Tool Use

Core claim: Web3 Tool Use turns RPC, contract reads, transaction generation, wallet confirmation, explorers, and DeFi operations into Agent-callable tools. The hard part is not “can the model call it”, but permission, parameters, simulation, and audit logs.

First principles:

- Model may choose tools, but deterministic boundaries must constrain tool execution.
- Read/write must be separated.
- Parameters such as chain id, contract address, method, args, value, and slippage must be structured, not hidden in natural language.
- Every call needs logs: input, output, time, source, error, chain id, block number, tx hash, confirmation, and policy result.

Minimal artifact checklist:

| Tool | Risk | Required boundary |
|---|---|---|
| RPC read | Low / medium | chain id, provider, block number, method, result |
| Contract read | Medium | verified contract, ABI match, network check |
| Transaction draft | High | no broadcast, explicit calldata, simulation-ready |
| Wallet action | High | separate connect / sign / send / approve / revoke |
| DeFi action | Very high | protocol whitelist, amount cap, slippage cap, simulation, allowance check, human or policy confirmation |

## Chapter notes — Agent Workflow

Core claim: Agent Workflow turns “user goal → context read → plan → tool call → risk check → execution → record/review” into a controlled process instead of free-form model behavior.

First principles:

- High-risk Agent systems cannot rely only on next-token reasoning; they need state, boundaries, and stopping conditions.
- Workflow must be explicit, recoverable, and replayable.
- Trace and regression sets are not observability nice-to-haves; they are safety infrastructure.

Minimal workflow skeleton:

```text
user_goal
→ load_chain_context
→ check_balance_and_allowance
→ query_price_and_liquidity
→ draft_transaction
→ simulate_transaction
→ policy_check
→ human_confirmation_if_required
→ submit_or_cancel
→ track_receipt
→ write_trace_and_daily_note
```

State examples:

```text
draft → context_loaded → plan_ready → simulation_failed / waiting_user_confirmation → submitted → confirmed / reverted / cancelled
```
